## 二、P0 待修（3 项）

### 02 API key 吊销 / 轮换 + 可选清史

- 事实：`git rm` 只移除当前快照。621168f 之前的历史提交仍完整保留两个涉事文件的 blob；GitHub 远程仓库同样持有。任何获得仓库读权限的主体都可恢复这些 key。
- 修复（按优先级）：
  1. 【用户动作，不可代理】在各供应商平台（豆包 / Kimi / DeepSeek / GLM / 通义）吊销全部涉事 key 并签发新 key；新 key 只走本地 env，绝不入库。
  2. 【待产品决策】git 历史清除：`git filter-repo` 删除两个路径的全历史 + force push。破坏性操作（所有 clone 失效、开源协作者需重新克隆）。在「仓库私有 + key 已轮换」前提下，清史为可选项而非必选项。
- 关闭条件：全部 key 轮换完成并在本表标记。

### 03 CI 缺失

- 证据：仓库根无 `.github/workflows` 目录。历史上质量验证依赖「生产服务器 Docker 容器内手工执行」——生产环境兼任 CI：结果不可追溯、无法阻止坏提交合入、且与生产部署耦合。
- 修复：等待 `docs/research/` 的 CI 调研报告落地后建 GitHub Actions：
  - 第一阶段（无测试也可上线）：lint + typecheck + check:surfaces + build，push/PR 触发。
  - 第二阶段：接入测试 job（依赖 04 的测试重建）。

### 04 测试体系真空

- 现状：门禁 = check:surfaces + lint + typecheck + build，全部为静态检查，无任何运行时验证。回归风险完全靠人工目测。
- 修复：按 `docs/research/` 调研报告分阶段重建：
  1. 引擎 / 解析器纯函数单测（games/*/engine、A2A 消息解析）——收益最高、依赖最少；
  2. API route 集成测试（match 生命周期、auth）；
  3. E2E（Playwright 覆盖建局 → 观赛 → 结算主链路）。
