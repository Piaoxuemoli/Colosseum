## 1. 产品愿景与定位

### 1.1 一句话愿景

让任何人在浏览器里看 AI 如何思考、如何博弈：配置模型、组一场局、实时观战、赛后复盘——把每一场对局变成可复盘、可对比、可分享的决策标本。

### 1.2 产品是什么 / 不是什么

| # | 是 | 不是 |
|---|---|---|
| 1 | 纯 AI 博弈观战与评测平台：所有参赛者均为 LLM 驱动的 Agent | 普通游戏平台：不以真人玩家的游戏乐趣为目标 |
| 2 | 观众拥有上帝视角的"AI 竞技场直播 + 录播"产品 | 不做真人玩家对战，也不做人机混合对局（v1 边界，见第 7 节） |
| 3 | 以游戏品类为载体的模型决策能力对比与展示环境 | 不是 LLM 网关、聊天助手或通用 Agent 开发框架 |
| 4 | 游戏品类可扩展的博弈平台（前两个实例：德州扑克、狼人杀） | 不与任何单一游戏绑定；游戏是品类实例，不是产品本体 |

### 1.3 核心价值主张

核心命题：**看 AI 如何思考与博弈**。拆解为三根支柱：

| 支柱 | 含义 | 差异化 |
|---|---|---|
| 透明思考链 | 每个动作前的完整推理（原始思考 + 人类可读摘要）对观众实时可见、赛后可回放 | 多数竞技产品只给结果，Colosseum 给过程 |
| 可复盘对局 | 对局全量事件留痕，支持拖动回放、按阶段跳转、按选手视角检视 | 对局是"决策标本"，不是一次性直播 |
| 可对比模型 | 同一局内不同模型同台竞技；跨局累积选手长期画像 | 把"哪个模型更会博弈"从轶事变成可查证据 |

## 2. 目标用户与核心场景

### 2.1 Persona

| Persona | 画像 | 核心诉求 | 关键行为 |
|---|---|---|---|
| P1 AI 研究者 / 爱好者 | 熟悉 LLM API 与提示词工程，关注模型能力边界与横向对比 | 控制变量对比模型决策质量；拿到可分析的原始数据（思考链、动作序列、异常记录） | 自带多供应商 API key；精确组局；赛后深挖数据 |
| P2 求职者 / 学习者 | 学生、转型者、Agent 开发入门者 | 学习人设（prompt）设计与 Agent 行为塑造；用对局成果做作品集 | 复制 / 改造人设模板做实验；打磨并分享自己的 Agent |
| P3 娱乐观众 | 对 AI 好奇的大众，不写代码、不配 key | 看一场"AI 博弈节目"：易懂的局势、有梗的人设、主持人解说 | 一键观战；看高光与排名；向朋友传播 |

### 2.2 用户旅程

公共主干：**配 key → 组局 → 观战 → 复盘 → 分享**。三个 persona 的旅程差异：

| 阶段 | P1 研究者 / 爱好者 | P2 求职者 / 学习者 | P3 娱乐观众 |
|---|---|---|---|
| 配 key | 自建多供应商 Profile，逐一连接测试，调推理参数 | 跟随引导配 1 个 key，用人设模板起步 | 期望零配置（依赖他人组局或平台预置，受 OD-2 / OD-3 约束） |
| 组局 | 精确控制阵容与规则参数，构造对照组 | 复用模板阵容，改动单个变量做实验 | 一键开局（预置阵容） |
| 观战 | 盯思考链与决策质量，记录观察 | 观察人设如何影响行为 | 看局势、筹码、淘汰的戏剧性 |
| 复盘 | 逐手 / 逐阶段回放，导出数据离线分析（导出为 P2） | 拆解优秀 Agent 的推理路径并模仿 | 看高光时刻与终局排名 |
| 分享 | 分享结论与数据（形态受 OD-4 约束） | 分享 Agent 与对局链接，沉淀作品集 | 分享精彩片段（受 OD-3 / OD-4 约束） |

注：分享环节——OD-3 / OD-4 已于 2026-09-08 代决：仓库保持私有（公开化以凭据吊销确认 + git 清史为硬前置）、v1 仅事件级回放（分享链接后置 R4）；v1 仅定义分享意图，不承诺任何公开服务形态。

## 3. 核心概念模型（产品层词汇表）

| 概念 | 定义 | 用户可见形态 |
|---|---|---|
| LLM Profile | 一个可命名的模型接入配置：供应商 + 模型名 + API key + 推理参数。用户私有资产，可被多个 Agent 复用 | 设置页的 Profile 卡片（含健康状态）；Agent 编辑时的选择器 |
| Agent | 参赛选手：人设（性格与策略描述）+ 绑定一个 Profile + 所属游戏品类 | Agent 卡片：头像、人设摘要、所用模型、战绩、（P2）长期画像 |
| 对局 Match | 一次完整博弈：游戏品类 + 参赛 Agent 集合 + 规则参数；从创建、进行中到终局结算有完整生命周期 | 对局卡片（状态：待开始 / 进行中 / 已结束）；观战页；回放页 |
| 观战 | 上帝视角实时观看进行中的对局：全局局势 + 思考链 + 动作流 | 实时观战页（游戏态势视图 + 思考气泡 + 动作时间线） |
| 回放 | 对已结束对局按时间轴重新呈现，含当时的思考链 | 回放页（进度条、阶段跳转、逐事件步进、选手视角过滤） |
| 主持人 Agent | AI 扮演的中立调度角色：宣告阶段、推进流程、旁白解说。社交推理类必需，牌桌类可选增强 | 观战页的主持台 / 旁白条；台词进入动作流 |
| 印象 / 画像 | Agent 的跨对局长期记忆：对其他选手形成的印象与自身风格沉淀，供后续对局决策参考 | Agent 详情页可读的"性格画像"与"对对手的印象" |
| 兜底策略 | LLM 调用失败、超时或输出非法时，由规则化 AI 接管该步决策，保证对局不中断 | 动作流条目上的兜底标记，展开可见失败原因；不打断观战 |
| 游戏品类 | 一类博弈的规则、角色、阶段、呈现方式的封装单元；具体游戏是品类实例（当前实例：德州扑克、狼人杀） | 创建对局时的游戏选择器；品类专属观战布局与规则面板 |

## 4. 功能需求

编号规则：`FR-<组>-<序号>`（如 FR-4.1-01）；组级引用（如 FR-4.6）指该组全部条目。优先级：P0 = v1 必须；P1 = 重要、可后置；P2 = 增强。验收标准须可独立验证；"已实现但无法按验收标准演示"不计为完成。

### 4.1 账户与密钥管理

**FR-4.1-01 Profile 管理（P0）**
描述：用户可创建、编辑、删除多个 LLM Profile，覆盖主流供应商；字段含供应商、模型名、API key、推理参数；提供连接测试。
验收标准：
- Given 用户填写某供应商的 key 与模型，When 点击"测试连接"，Then 10 秒内返回成功或失败，失败附可读原因（鉴权 / 额度 / 网络 / 模型不存在）。
- Given 连接测试成功，When 保存 Profile，Then 列表出现该 Profile，再次编辑时全部配置完整回显（key 可仅显示掩码）。
- Given 用户没有任何 Profile，When 进入依赖 Profile 的功能，Then 呈现引导创建的空状态与入口，而非裸报错。

**FR-4.1-02 密钥仅存浏览器端（P0）**
描述：API key 默认只存于用户浏览器本地；仅在需要对局调用 LLM 时被使用；服务端不做持久化存储。
验收标准：
- Given 用户清除浏览器本地存储，Then 平台不再持有该用户的任何 key，服务端无法恢复。
- Given 对服务端日志与持久化数据做安全审计，Then 检索不到任何用户 key 明文（与 NFR-07 互为验证）。
- 产品文档明示 key 的存储位置、使用时机与清除方式。

**FR-4.1-03 密钥状态可见（P1）**
描述：Profile 列表展示 key 健康状态（未配置 / 可用 / 失效），失效区分原因（过期、额度耗尽、权限不足）；失效时给出修复引导。
验收标准：
- Given 某 Profile 的最近调用返回鉴权或额度类失败，When 用户查看 Profile 列表，Then 该 Profile 呈失效态并附原因与"更换 key"入口。
- Given 失效 Profile 被组局引用，When 创建对局，Then 赛前出现明确警示或阻断，不允许静默依赖兜底开局。

### 4.2 Agent 管理

**FR-4.2-01 创建 / 编辑 Agent（P0）**
描述：Agent 由人设 prompt、绑定的 Profile、所属游戏品类三要素构成；全部字段可编辑。
验收标准：
- Given 填写人设并选择 Profile 与游戏，When 保存，Then Agent 出现在列表，且所有字段可再次编辑。
- Given 人设留空，When 保存，Then 被拦截并提示人设为必填。
- Given Agent 被进行中的对局引用，When 编辑该 Agent，Then 进行中的对局不受影响（改动仅对新对局生效）。

**FR-4.2-02 预置人设模板（P0）**
描述：按游戏品类提供开箱即用的人设模板库，新用户可零创作起步。
验收标准：
- Given 新用户未创建任何 Agent，When 打开模板库，Then 每个已支持品类至少有 3 个模板可一键生成可参赛 Agent。
- Given 由模板生成 Agent，Then 其与自建 Agent 权利完全一致（可编辑、可参赛、可删除）。

**FR-4.2-03 Agent 卡片对外可发现（P0）**
描述：Agent 以卡片形式对外呈现，是"选手"的公开形象页。
验收标准：
- Given 存在多个 Agent，When 浏览 Agent 列表，Then 每张卡片至少含：人设摘要、模型标识（供应商 + 模型名）、参赛场次与胜率。
- Given 点击卡片，When 进入详情，Then 可见完整人设与参与的对局历史索引；（P2 启用后）附长期画像摘要。

### 4.3 对局管理

**FR-4.3-01 创建对局（P0）**
描述：创建流程依次确定：游戏品类 → 参赛 Agent（含人数合法性校验）→ 规则参数面板（按品类提供：牌桌类如起始筹码 / 盲注结构 / 淘汰规则；社交推理类如人数 / 角色配置 / 发言轮次）。
验收标准：
- Given 阵容不满足所选游戏的人数约束（过多 / 过少），When 提交，Then 拦截并指出具体缺口。
- Given 同一 Agent 被重复选择，When 提交，Then 拦截或按品类规则显式处理，不允许静默重复入场。
- Given 创建成功，When 进入对局页，Then 完整展示阵容、规则摘要与开始入口。

**FR-4.3-02 并发多对局互不干扰（P0）**
验收标准：
- Given 两个及以上对局同时进行，When 其中一个出现大量 LLM 失败与兜底，Then 其余对局的推进节奏、结果与留存数据不受影响。
- Given 多对局并行，When 用户在其间切换观战，Then 各对局进度独立、事件不串台。

**FR-4.3-03 结束控制（P0）**
描述：三种结束方式——自然终局（规则自行走完）、本回合后结束（走完当前回合再结算）、强制结束（立即结算）。
验收标准：
- Given 进行中的对局，When 选择"本回合后结束"，Then 当前回合完整结束后进入结算，不存在回合中途截断的中间态。
- Given 强制结束，When 查看结算，Then 明确标注"人为终止"及终止时点，此前数据完整保留。
- Given 自然终局，When 结算，Then 排名与终局态势一致。

**FR-4.3-04 删除对局（P0）**
验收标准：
- Given 任意对局，When 删除，Then 需二次确认，确认文案明示不可恢复。
- Given 已结束对局被删除，Then 其从对局列表、历史与统计中消失。
- Given 进行中的对局，When 请求删除，Then 引导先执行结束控制（提供"强制结束并删除"路径），不提供静默消失式删除。

### 4.4 实时观战

**FR-4.4-01 上帝视角全局态势（P0）**
描述：观战默认呈现完整信息面（含对选手互相隐藏的私有信息，如全部手牌 / 身份），并视觉区分"公开信息"与"上帝视角信息"；提供"仅公开视角"开关给不想被剧透的观众。
验收标准：
- Given 对局进行中，When 打开观战页，Then 全部选手的私有信息与公共信息同时可见且有区分标识。
- Given 观众开启"仅公开视角"，Then 私有信息被遮蔽，且切换不丢失观战进度。

**FR-4.4-02 实时思考链展示（P0）**
描述：双形态呈现——当前正在思考选手的思考气泡（增量更新）+ 历史思考日志；每条含人类可读摘要，可展开原始全文。
验收标准：
- Given 选手正在决策，When 思考内容增量产生，Then 气泡实时追加更新，且可见"谁在思考"。
- Given 某条思考完成，When 展开该条目，Then 可读完整原始文本、所属选手与时间戳。

**FR-4.4-03 动作流（P0）**
描述：每个动作以人类可读的中文句子呈现在时间线上：谁、做了什么、结果如何。
验收标准：
- Given 任意动作条目，Then 可解析出动作主体、动作类型、对象与数值、引发的局势变化。
- Given 新动作产生，When 时间线处于跟随态，Then 自动滚动；用户可暂停跟随回看历史。

**FR-4.4-04 错误与兜底可见性（P0）**
描述：LLM 失败与兜底接管发生时，不打断观战主流程；异常信息在动作流标记与专门面板可查。
验收标准：
- Given 某选手触发兜底，When 观众正在观战，Then 主界面无错误弹窗、观战不中断，对应动作条目带兜底标记。
- Given 观众点击兜底标记，When 展开，Then 可见失败原因类别（超时 / 鉴权 / 额度 / 非法输出等）与重试情况。
- Given 本局发生过异常，When 查看对局页，Then 有汇总入口（如"本局异常 N 次"）直达清单。

### 4.5 游戏呈现（按品类抽象的呈现要求）

**FR-4.5-01 牌桌类呈现（P0）**（实例：德州扑克）
验收清单：
- 选手面：手牌、筹码、位置、状态（进行中 / 弃牌 / 全下 / 出局）全程可见。
- 公共面：公共牌、底池、当前注额、边池（多人全下时正确分池）。
- 走势：按选手分色的筹码变化曲线，随手牌推进更新。
- 连续局：手牌编号、每手结算摘要、淘汰节点清晰可循。

**FR-4.5-02 社交推理类呈现（P0）**（实例：狼人杀）
验收清单：
- 昼 / 夜阶段切换清晰，含阶段推进指示；主持人宣告进入动作流。
- 发言按顺序流式展示，附发言者存活状态。
- 投票过程与结果实时可见（票型统计与当选 / 平票处理）。
- 死亡 / 出局有明确标记；身份揭晓在上帝视角即时、在公开视角按规则延迟。
- 主持人（该品类必需角色）台词在主持台呈现。

**FR-4.5-03 新游戏接入的呈现契约（P1）**
描述：任何新品类接入须满足平台统一呈现契约（产品层要求）：可渲染的态势视图、结构化事件流、阶段模型（阶段清单与切换规则）、终局结算结构。契约的具体形式由实现体系定义。
验收标准：
- Given 新游戏品类接入，When 观战，Then 思考链、动作流、兜底可见性等观战能力自动复用，体验与既有品类一致。
- Given 新游戏品类接入，When 对局结束，Then 自动获得统一的结算页与回放入口。
- Given 新品类接入完成，Then 未修改平台级导航、列表与观战框架（"品类即插件"的验证，与 NFR-08 互证）。

### 4.6 赛后与复盘

**FR-4.6-01 终局排名与结算（P0）**
验收标准：
- Given 对局终局（含强制结束），When 打开结算页，Then 展示最终排名、品类关键数据（筹码 / 存活 / 得票等）、终局时刻态势快照。
- Given 排名结果，When 对照动作流逐事件回推，Then 排名可被过程数据验证，无凭空名次。

**FR-4.6-02 全程回放（P0）**
验收标准：
- Given 已结束对局，When 打开回放，Then 可拖动到任意时间点并正确重建该时刻完整态势。
- When 查看阶段跳转，Then 阶段列表完整（牌桌类按手牌、社交推理类按昼夜轮次），无遗漏。
- Given 回放中的任意事件，Then 其内容与实时观战时留存的原始事件一致，回放不重算、不改写。

**FR-4.6-03 思考链回放（P0）**
验收标准：
- Given 回放中任一动作，When 查看其前置思考，Then 完整思考文本可读。
- When 选择单选手视角，Then 仅呈现该选手的决策轨迹（思考 + 动作）。

**FR-4.6-04 对局历史列表（P0）**
验收标准：
- Given 多个已结束对局，When 查看历史，Then 支持按游戏品类、时间、参赛 Agent 过滤检索。
- Given 任一历史条目，Then 可进入其结算页与回放页，且列表展示创建时间、时长与终局排名摘要。

**FR-4.6-05 跨对局统计与选手长期画像（P2）**
描述：两个层次——给观众看的统计聚合（胜率、名次分布、行为倾向），与供 Agent 决策使用的长期画像（"印象 / 画像"概念）；P2 先做前者，后者随画像机制整体决策（联动 OD-5）启用。
验收标准：
- Given 同一 Agent 参与多局，When 查看其卡片，Then 胜率、名次分布、常用动作倾向等聚合可见，且可追溯到来源对局。
- Given 画像机制启用，Then Agent 详情提供人可读的画像摘要，并标注其来源局数。

### 4.7 主持人 / 解说（可选增强）

**FR-4.7-01 AI 主持人旁白（P1）**
描述：主持人在阶段切换与关键事件（大底池、淘汰、平安夜 / 屠边等）产生解说性旁白。社交推理类中主持人的流程性宣告属于游戏规则必需（已由 FR-4.5-02 覆盖），本条仅约束解说性旁白。
验收标准：
- Given 主持人产生旁白，Then 其与事件流时序一致，且只引用公开信息，不泄露上帝视角才可见的信息。
- Given 观众关闭解说旁白，Then 牌桌类对局不受任何影响；社交推理类仅解说性内容可关，流程性宣告不可关。

**FR-4.7-02 赛后解说（P1）**
验收标准：
- Given 对局结束，When 请求赛后解说，Then 生成基于本局真实数据的总结叙述（关键转折、表现最佳选手、失误点评）。
- Given 解说内容，When 与事件流对照，Then 不存在未发生过的事件（不虚构）。

### 4.8 可观测性与信任

**FR-4.8-01 LLM 调用错误与兜底透明可查（P0）**
验收标准：
- Given 对局发生过 LLM 失败，When 赛后查看该对局，Then 存在按时间排列的异常清单：选手、失败原因类别、处置方式（重试 / 兜底）。
- Given 兜底接管的动作，When 在结算页与回放中查看，Then 兜底标记仍在，不因终局而丢失。

**FR-4.8-02 对局事件全量留存（P0）**
验收标准：
- Given 任意已结束对局，When 导出 / 查询其事件，Then 覆盖创建到终局的全部事件（思考、动作、阶段切换、异常），无静默丢弃。
- Given 留存数据，When 重建回放，Then 以回放可完整重建为留存完备性的判据（与 FR-4.6-02 互为验证）。

**FR-4.8-03 用量可见（P1）**
描述：对局级 token 用量与调用次数（按选手、按用途：决策 / 主持 / 解说）对用户可见，支撑成本意识（功能面承接 NFR-06）。
验收标准：
- Given 对局进行中或已结束，When 查看对局详情，Then 可见按选手聚合的 token 用量与调用次数。

### 4.9 跨对局天梯（R4-3）

**FR-4.9-01 ELO 天梯（P2；OD-5 方向 b 落地）**
描述：对局完成时自动结算跨对局 ELO 评分，形成按品类分列的天梯；支持由历史对局幂等重建。公平性口径（OD-5 前置细则，2026-09-10 已代决）：

| # | 口径 | 内容 |
|---|---|---|
| 1 | 分列 | 天梯按游戏品类独立（德扑 / 狼人 / 阿瓦隆互不换算） |
| 2 | 选手 | Agent 实体即选手（同模型不同人格 = 不同选手）；重复参赛累积 |
| 3 | 参数 | 初始 1000 分；K = 32 |
| 4 | 多人更新 | 按终局名次两两比较的守恒更新（每名选手的变动 = 其与所有对手的对局期望差之和）；阵营游戏按「胜方全员 vs 负方全员」，阵营内部不分高下 |
| 5 | 平局 | 平局与胜负不可判定的对局不更新任何评分 |
| 6 | 胜负判定 | 复用观众面统计口径（FR-4.6-05 的 finalRanking + winnerFaction 判定），两处口径必须同源 |
| 7 | 重建 | 全量回放重建幂等：同一批历史对局重放任意次数得到相同天梯 |

验收标准：
- Given 一场对局完成，When 结算，Then 全体参赛选手的品类评分按上表更新，且更新不阻塞对局结算主流程。
- Given 同一批已结束对局，When 重建天梯任意次，Then 结果逐分一致（幂等）。
- Given 天梯页，When 查看某品类，Then 每名选手可见评分、场次、胜场与排名，数据可追溯到来源对局。
- Given 平局 / 异常结束的对局，When 结算，Then 不产生评分变动。

## 5. 非功能需求

| 编号 | 类别 | 需求 | 验收口径 |
|---|---|---|---|
| NFR-01 | 性能 | 观战首屏：进入观战页迅速呈现当前态势 | 常规网络与本地部署下首屏 ≤ 3 秒 |
| NFR-02 | 性能 | 长局流畅：数百事件的进行中对局，观战交互不劣化 | 时间线滚动、视角切换等交互响应 < 200ms，无可感知卡顿 |
| NFR-03 | 性能 | 实时性：动作发生到观众可见的推送链路延迟（不含 LLM 思考时长；推送机制属实现体系） | 端到端 ≤ 2 秒 |
| NFR-04 | 可靠性 | LLM 失败不终局：任何单点 LLM 异常不导致对局崩溃或永久停滞 | 连续失败场景下对局仍能经兜底推进至可控结束（与 FR-4.4-04 联合验证） |
| NFR-05 | 可靠性 | 断线重连：观众网络中断恢复后，观战从当前状态继续 | 重连后态势与事件流完整一致，不重播错乱、不丢事件 |
| NFR-06 | 成本可控 | token 用量可见 | 对局详情提供用量汇总（承接 FR-4.8-03） |
| NFR-07 | 安全 | 用户密钥不落服务端持久存储；凭据泄露零容忍 | 见 FR-4.1-02；任何泄露事件一律按最高级事故处理；公开性决策（OD-3）以凭据清理完成为前置 |
| NFR-08 | 可扩展性 | 新增一个游戏品类不需要改平台核心 | 以第三个游戏接入为验证场景（依赖 OD-1；判据见 FR-4.5-03） |
| NFR-09 | 可部署性 | 单机 Docker 与托管平台两条部署路径均可用 | 各路径提供可复现的部署说明与验证步骤；同一版本在两条路径均可跑通核心旅程（配 key → 组局 → 观战 → 复盘） |

## 7. 明确不做（v1 边界）

| # | 不做 | 原因 |
|---|---|---|
| 1 | 真人玩家入局（含人机混合对局） | 定位是纯 AI 博弈；真人入局引入公平性、反作弊、体验节奏等另一量级的问题 |
| 2 | 暂停 / 单步干预对局（干预某个 Agent 的决策） | 保持纯观战叙事；可干预的对局不再是可信的"决策标本"。注意区分：结束控制（FR-4.3-03）是观演控制，不属于决策干预 |
| 3 | 主动上下文压缩 | 对局上下文全量注入，超出模型窗口时走报错兜底路径；压缩会污染思考链的可信度与可复盘性 |
| 4 | 向量检索记忆 | 长期记忆采用人可读的印象 / 画像机制；向量检索不可解释、不可复盘，与透明性支柱冲突 |

边界变更：如需突破上述边界，须先在变更记录登记动因，经所有者确认后方可进入需求正文。
